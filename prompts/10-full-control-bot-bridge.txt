PRODUCT INTENT
Serenox already operates a Telegram user account and supports ordinary
owner-authored commands, inline handlers, callbacks, forms, lists, and
galleries. Add a second, optional control surface: the owner's own Telegram
bot can be attached to one Serenox account and used to invoke only explicitly
exposed control commands through `@bot query`, private bot commands, and
bounded inline keyboards.

The bot is a UI and transport adapter, not a second user session and not a
general-purpose chatbot. Plugin business logic still runs inside the existing
bounded, supervised executor. Actions that change the owner's Telegram account
continue to use the user session; actions that render the control UI use the
Bot API transport. The distinction must be explicit in the protocol and action
execution path.

The existing inline-command/inline-handler surface remains supported. This
feature must extend it with a real Bot API transport and an opt-in control
command surface, not replace or silently reinterpret existing inline handlers.

SCOPE
This task includes the complete supported control-bot product surface:

- secure bot-token attachment, verification, persistence, rotation, detach,
  status, start, stop, polling, reconnect, and shutdown;
- inline mode through `@bot query`;
- private-chat bot commands and help, where useful for multi-step flows;
- typed control-command invocation with owner/allow-list authorization;
- Bot API inline results, bounded forms, callback buttons, URL buttons, and
  switch-inline buttons;
- callback handling for both ordinary bot messages and inline messages;
- edit/delete/answer operations for control-bot UI messages;
- plugin metadata and permissions that expose only selected commands;
- shared bounded queues, deadlines, rate limits, action results, idempotency,
  observability, lifecycle, and cleanup;
- Go and Python SDK/sidecar parity;
- deterministic fake-Bot-API, recorded, supervised, and opt-in live-bot tests.

This task does not add arbitrary Bot API method dispatch, a public webhook
server, a generic bot hosting platform, multi-tenant bots, plugin-controlled
network sockets, or a way for arbitrary users to operate the user account.
Webhook support may remain explicitly unsupported unless the repository has a
separately reviewed inbound-listener design with equivalent authentication and
resource controls. Long polling is the required production transport for this
task.

OBJECTIVE
Make the attached bot a first-class, secure, bounded control transport. A
plugin author must be able to declare a command as bot-exposed and implement a
flow such as:

```text
User types: @my_serenox_bot foundation
        ↓
Bot API inline query arrives at Serenox
        ↓
Serenox returns one or more bounded inline results
        ↓
User selects a result or presses a callback button
        ↓
Plugin receives a typed control event
        ↓
Plugin renders the next UI step through the Bot API
        ↓
Any user-account mutation is executed through the user-session action path
```

Typing an inline query must not silently perform a destructive or irreversible
operation. State-changing flows require an explicit result selection, button
press, confirmation, or private-chat command according to the declared command
policy.

ACCEPTANCE CRITERIA
1. A verified bot token can be attached, persisted securely, rotated, detached,
   and started without leaking the token or replacing a working bot on failed
   verification.
2. Long polling is bounded, cancellable, reconnecting, offset-aware, and does
   not starve ordinary user-session commands or watchers.
3. A plugin can explicitly expose a command through `@bot query`, private bot
   chat, or both, while non-exposed commands remain unavailable through the
   bot.
4. Inline queries return bounded, validated results with inline keyboards and
   callback buttons. Callback answers and inline-message edits work through
   typed DTOs, including `inline_message_id` where applicable.
5. Existing inline handlers, forms, lists, galleries, callback routes, and
   command behavior remain compatible unless a documented migration is needed.
6. Bot UI actions and user-session Telegram mutations use separate explicit
   response channels and permissions. A bot event never bypasses the ordinary
   owner-command security model.
7. Owner/allow-list, plugin/account binding, flow binding, callback TTL,
   confirmation, rate limits, deadlines, and idempotency are enforced in the
   core before every relevant operation.
8. Go and Python plugins have equivalent typed APIs without raw Telegram
   objects, Bot API clients, tokens, sockets, or arbitrary method dispatch.
9. Recorded, fake-live, supervised Go/Python, and opt-in live fixtures cover
   every claimed behavior. Live verification is clearly separated from
   credential-free verification.
10. Bot polling, callbacks, flows, inline units, queues, frames, actions,
    metrics, temporary media, RPC waiters, and secrets remain bounded and are
    cleaned on timeout, crash, restart, unload, detach, rotation, and shutdown.
11. No action reports fabricated success or fabricated message IDs. Ambiguous
    Bot API or user-session mutations are represented explicitly.
12. Documentation and compatibility matrices accurately list implemented,
    live-verified, partial, unsupported, and intentionally out-of-scope
    surfaces.

PRODUCT INTENT

Autopilot lets the owner describe small, finite automations such as:

```text
message matches a bounded rule
  -> record a run
  -> send a notification or call one approved connector
  -> wait through a durable Serenox job
  -> request owner approval through the control bot
  -> continue, cancel, or fail explicitly
  -> retain a bounded audit summary
```

Representative uses include delayed reminders, approval flows, daily digests,
incident follow-ups, safe webhook/API workflows, and demonstrations of restart
recovery. Autopilot is deliberately not Zapier, n8n, a programming language,
or a shell hidden inside Telegram.

The ordinary plugin must work without a control bot and without external
network access. Control-bot and HTTP functionality are optional enhancements
that degrade to explicit `unavailable` states. The default built-in demo must
remain deterministic and useful in recorded mode.

NON-GOALS AND HARD BOUNDARIES

Do not add any of the following:

- arbitrary Go, Python, JavaScript, Lua, template expression, or shell
  execution;
- `eval`, `exec`, runtime compilation, runtime package installation, raw
  subprocess commands, or user-supplied binaries;
- arbitrary Telegram, Bot API, gotd, Pyrogram, Telethon, SQL, Redis, S3,
  filesystem, socket, or `net/http` access;
- arbitrary URLs supplied at workflow execution time;
- unbounded cron syntax, loops, recursion, backward workflow jumps, dynamic
  goroutines, hidden retries, or unbounded fan-out;
- cross-plugin invocation or access to another plugin's state/jobs;
- exactly-once claims for Telegram or HTTP mutations;
- secrets in workflow definitions, audit events, logs, metrics, job payloads,
  commands, or documentation fixtures;
- changes to the plugin protocol merely to make the example look complete.

Autopilot must use only the typed, permission-checked SDK surface. If a needed
operation is absent or partial, either design a clear degraded behavior or make
the smallest generally useful SDK/core fix with focused tests and documentation.
Any core change must be justified independently of Autopilot and must not add a
plugin-specific escape hatch.

2. Define a finite versioned workflow model.

   Implement a plugin-local specification such as `autopilot.workflow/v1` with
   explicit, bounded fields. The exact Go names may follow repository style,
   but the model must contain:

   - stable workflow ID, display name, description, enabled state, revision,
     created/updated timestamps, and definition version;
   - exactly one trigger definition;
   - a finite ordered list or acyclic forward-only graph of typed steps;
   - owner/account binding supplied by the host context rather than user text;
   - optional concurrency, cooldown, and run-retention policy within strict
     plugin limits;
   - explicit validation errors with field paths;
   - canonical serialization suitable for durable storage and tests.

   Suggested default ceilings:

   - at most 32 active workflow definitions;
   - at most 16 steps per workflow;
   - at most 32 state transitions per run;
   - at most 64 retained runs and 256 audit summaries in total;
   - workflow names up to 64 UTF-8 bytes and descriptions up to 256 bytes;
   - definition size up to 32 KiB;
   - run context up to 16 KiB;
   - rendered action text up to the lower of Telegram and protocol limits;
   - no more than one waiting job and one waiting approval per run.

   Use stricter values when required by the actual manifest/SDK limits. Put all
   effective limits in one validated policy object and document them.

3. Implement a deliberately finite trigger catalog.

   Support coherent triggers that can be implemented using current Serenox
   APIs, for example:

   - manual trigger through an owner command;
   - incoming or outgoing message watcher with bounded combinations of exact,
     prefix, suffix, contains, and Go RE2-compatible regular expression match;
   - optional chat/sender scope when the current event DTO supports it;
   - one-shot scheduled trigger;
   - fixed-delay/fixed-rate or calendar trigger with explicit IANA timezone.

   Compile and validate regular expressions once per workflow revision. Bound
   expression length and count. Dynamic workflow matching may happen inside one
   declared watcher when handler metadata cannot change at runtime, but the
   watcher and in-memory index must remain bounded and must reject commands by
   default to prevent feedback loops.

   A workflow must not trigger recursively from its own generated message. Use
   host-provided direction/source metadata plus an explicit run marker or a
   bounded deduplication strategy. Do not hide recursion prevention in message
   text visible to users.

4. Implement a finite typed step catalog.

   At minimum implement useful subsets of:

   - `notify`: send or reply through the user-session action channel;
   - `wait`: suspend through a persistent one-shot host job;
   - `approval`: request an owner decision through the attached control bot;
   - `http`: make a bounded request to a named connector whose exact origin is
     declared in the signed package manifest;
   - `set`: assign a bounded JSON scalar/object value to the run context;
   - `condition`: select a forward-only success/failure branch using finite
     comparisons, never an expression evaluator;
   - `complete` and `fail`: terminate with an explicit summary.

   Steps must not jump backward. Validate that the graph is acyclic and that
   every path terminates within the transition limit. A step may select only a
   higher step index or a terminal state. Do not implement loops through jobs,
   callbacks, conditions, or workflow-to-workflow invocation.

5. Implement safe bounded template rendering.

   Templates may substitute only documented fields such as:

   ```text
   {{workflow.id}}
   {{run.id}}
   {{message.text}}
   {{message.chat_id}}
   {{http.status}}
   {{approval.decision}}
   {{vars.name}}
   ```

   Use an explicit parser and allowlist, not Go `text/template` functions that
   could grow into a programming surface. Reject unknown variables, malformed
   braces, excessive expansion, recursive substitution, and non-scalar values
   where text is required. Escape/render Telegram text according to the action
   parse mode and cap the final UTF-8 byte length.

6. Define workflow run and state-transition semantics.

   A run must have at least:

   - bounded opaque run ID;
   - workflow ID and immutable workflow revision snapshot/digest;
   - state: pending, running, waiting_job, waiting_approval, completed, failed,
     cancelled, interrupted, or another documented finite enum;
   - current step/transition count;
   - bounded context and source summary;
   - created, updated, started, and finished timestamps as applicable;
   - expected job/approval identity where waiting;
   - bounded last error code and safe summary;
   - action/idempotency references sufficient for reconciliation without
     storing Telegram message bodies or secrets.

   Every transition must validate the expected state and revision before
   persistence. Duplicate job delivery, callback replay, repeated Telegram
   updates, or stale commands must not advance a run twice. Concurrent
   cancel/approve/job-complete operations must resolve deterministically.

7. Implement durable storage and recovery.

   Store workflow definitions, runs, indexes, and audit summaries only through
   namespaced host storage. Keep a documented schema version. Use batch/atomic
   operations when the existing storage API supports them; otherwise design a
   serialized mutation coordinator and explicit recovery invariant.

   On plugin start/restart:

   - validate stored schema and bounded cardinality before publishing ready;
   - rebuild only bounded derived indexes;
   - reconcile waiting runs with host job status;
   - mark a run that was actively executing during process exit as
     `interrupted`, never silently completed;
   - preserve waiting jobs/approvals only when their host-side identity is
     still valid and documented to survive;
   - expire stale approvals and runs deterministically;
   - never replay an ambiguous HTTP or Telegram mutation automatically;
   - make manual retry create an explicit new attempt/transition with a new
     operation identity where safe.

   Corrupt, oversized, unknown-version, or internally inconsistent state must
   fail closed with actionable recovery instructions. Do not discard all state
   silently.

8. Use the first-class Jobs API for all delayed and scheduled behavior.

   - approval expiration;

   Never call `time.AfterFunc`, create one timer/goroutine per workflow, or use

9. Implement typed HTTP connectors without turning Autopilot into a proxy.

   - whether the operation is read-only or mutating;

PRIMARY DELIVERABLE

Create a complete, polished, maintainable documentation website using
Fumadocs, Next.js App Router, TypeScript, and MDX. This is not an MVP, a visual
mockup, or a handful of placeholder pages. It must be a production-quality
docs-as-code system with a coherent information architecture, accurate English
documentation of the current Serenox product, fast local development,
full-text search, accessible responsive design, community contribution links,
automated verification, SEO, deployment configuration, and an explicit path to
future localization and release-versioned documentation.

The site should feel as deliberate and usable as a mature infrastructure or
developer-tool documentation portal while retaining a distinct Serenox visual
identity. Do not clone Vercel, Render, Mintlify, or another site's protected
branding, copy, illustrations, or layout pixel-for-pixel.

The canonical initial public locale is English. All navigation, prose, UI
labels, metadata, examples, diagrams, accessibility text, error explanations,
and contribution material delivered by this task must be in clear technical
English. Do not add partially translated pages, machine-translated filler, or a
language switcher containing unavailable languages.

HARD QUALITY RULES

- Do not ship lorem ipsum, TODO pages, empty categories, fake testimonials,
  invented benchmarks, fake API surfaces, unsupported commands, speculative
  compatibility promises, or decorative links that lead nowhere.
- Do not describe a feature as working merely because an earlier prompt asked
  for it, a DTO exists, or a documentation file claims it. Verify executable
  paths and tests. Label verified, partial, experimental, planned, and
  unsupported behavior honestly and consistently.
- Never publish Telegram API credentials, tokens, session data, real phone
  numbers, local absolute paths, signing secrets, or user-specific data.
- Keep examples deterministic and copy-pasteable. Clearly distinguish shell
  prompts, placeholders, expected output, and optional commands.
- Prefer ordinary Markdown for prose. Use MDX only where a real component
  improves comprehension. Content must remain readable in GitHub source view.
- Avoid a client-side JavaScript dependency for content that can be rendered
  statically or on the server.
- The production build must have no broken internal links, missing assets,
  hydration warnings, browser console errors, TypeScript errors, or failed
  content/schema validation.
- Preserve mobile usability, keyboard navigation, semantic landmarks, visible
  focus, reduced-motion preferences, sufficient contrast, and useful alt text.
- Do not add telemetry, cookies, third-party scripts, hosted fonts, or external
  analytics by default. Any optional analytics integration must be disabled
  unless explicitly configured and documented.

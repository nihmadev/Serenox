TERMINOLOGY

Call the product-level subsystem the Serenox Event Fabric. Use conventional,
descriptive protocol and package names such as `events`, `eventbus`,
`EventEnvelope`, `EventSubscription`, and `host.events`. Do not put a marketing
codename into the wire protocol. A future UI or product may call the subsystem
“Serenox Relay”, but protocol compatibility must not depend on that name.

PRIMARY DELIVERABLE

Implement a production-quality, bounded event fabric that lets supervised Go
and Python plugins publish versioned domain events and consume declared event
subscriptions without knowing another plugin's process, language, socket, or
installation path.

The intended composition model is:

```text
Telegram/control/job/core event
          -> core Event Fabric
          -> declared subscription and bounded delivery
          -> plugin worker
          -> zero or more typed actions and emitted events
          -> further declared subscribers
```

The core owns event identity, authentication, routing, persistence, admission,
retry scheduling, dead-letter state, quotas, cancellation, observability, and
lifecycle cleanup. Plugins own domain logic and explicitly declared event
schemas. The Event Fabric must reuse the existing supervisor, executor,
storage, Jobs/lifecycle, framing, permission, and action-result primitives. It
must not create a second plugin runtime, unbounded message broker, generic
pub/sub socket, or hidden distributed-system claim.

PRODUCT INTENT

Today Serenox plugins can respond to Telegram updates, commands, callbacks,
jobs, and host operations, but they are mostly isolated endpoints. The Event
Fabric turns them into composable workers. For example:

```text
telegram.message.received/v1
  -> voice detector
  -> media.transcribed/v1
  -> summarizer
  -> summary.created/v1
  -> knowledge-store and telegram-presenter
```

No subscriber receives an event merely because it uses a matching string.
Publishing, subscribing, source scope, account scope, payload size, delivery
class, and event namespaces must all be declared and permission checked.

The initial implementation is local to one Serenox daemon and one admitted
Telegram account runtime. It must be designed so the persistence interface can
later use PostgreSQL, but it must work correctly with the current file-backed
store and must not claim multi-node delivery, distributed consensus, or high
availability.

NON-GOALS AND HARD BOUNDARIES

Do not add any of the following:

- Kafka, NATS, Redis Streams, RabbitMQ, MQTT, AMQP, or another required broker;
- arbitrary plugin-owned sockets, ports, listeners, shared files, subprocess
  pipes, or direct process discovery;
- arbitrary reflection dispatch, runtime code loading, eval, shell, SQL, raw
  Telegram updates, gotd objects, access hashes, credentials, or secrets;
- unbounded wildcard topics, regex subscriptions, payload schemas, fan-out,
  retention, retries, backoff, event history, or replay;
- exactly-once delivery or exactly-once external side-effect claims;
- automatic replay of Telegram/HTTP mutations after an ambiguous result;
- atomicity claims across plugin storage, external effects, actions, and event
  publication unless one concrete transaction actually covers them;
- a second scheduler or worker pool hidden inside the fabric;
- cross-account publication or consumption by default;
- event payloads in metric labels or unrestricted diagnostic output.

2. Define a dedicated versioned event domain model.

   Introduce a finite DTO such as:

   ```json
   {
     "id": "evt_...",
     "type": "media.transcribed",
     "version": 1,
     "source": "plugin.example.voice",
     "account_id": 123,
     "occurred_unix_ms": 0,
     "correlation_id": "corr_...",
     "causation_id": "evt_parent",
     "trace_id": "trace_...",
     "dedupe_key": "optional-publisher-key",
     "content_type": "application/json",
     "payload": {}
   }
   ```

   Exact Go names may follow repository conventions, but define and validate:

   - host-assigned immutable event ID and trusted source identity;
   - lowercase namespaced event type and positive schema version;
   - account/plugin scope supplied by the host, never trusted from payload;
   - occurrence and durable-accept timestamps with clear clock ownership;
   - correlation, causation, trace, attempt, and hop metadata;
   - optional publisher-scoped deduplication key;
   - JSON payload with strict total, depth, string, collection, and field limits;
   - optional content/schema digest only if it has a verified consumer;
   - stable headers from a finite allowlist, not arbitrary secret-bearing maps.

   The host must overwrite identity, source, account, attempt, and routing
   fields. Unknown fields and invalid combinations must fail deterministically.
   Protocol evolution must be additive or explicitly negotiated.

3. Add explicit publication and subscription declarations.

   Extend plugin metadata and signed package policy with bounded declarations,
   for example:

   ```text
   publishes: media.transcribed/v1, voice.failed/v1
   subscribes: telegram.media.voice.received/v1
   ```

   Each publication declaration must define exact type/version, description,
   maximum payload bytes, delivery class, and optional schema descriptor.
   Each subscription must define exact type/version, stable handler ID,
   source/account policy, concurrency/admission class, maximum runtime, retry
   policy reference, and whether durable replay is accepted.

   Do not permit unrestricted `*`, `plugin.*`, regex, prefix, or user-supplied
   runtime subscriptions in v1. If narrowly bounded namespace matching is
   genuinely required, make it a separate high-risk capability with strict
   quotas and tests; exact matching remains the default.

   Validate consistency at package verification, handshake, activation, and
   restore. A process may advertise only declarations allowed by its signed
   `.srnx` manifest. Duplicate handlers, type/version conflicts, missing
   capabilities, excessive declarations, and undeclared publication must fail
   before activation.

4. Define least-privilege capabilities and permissions.

   Introduce explicit capabilities such as `events.publish` and
   `events.subscribe`, plus exact package permissions that cannot be widened by
   handshake metadata. Define a finite naming rule, for example:

   ```text
   event.publish.media.transcribed.v1
   event.subscribe.media.transcribed.v1
   ```

   If a more compact signed declaration is used, keep operation-to-permission
   mapping deterministic and exhaustively tested. Separate permissions for:

   - plugin domain publication;
   - consumption of another plugin's public domain event;
   - privacy-sensitive Telegram-derived core events;
   - administrative/core lifecycle events;
   - replay and DLQ inspection/management.

   Ordinary event permissions must never imply storage, HTTP, media, jobs,
   Telegram mutation, moderation, control-bot, secret, or future service-call
   permissions.

5. Implement bounded host publication.

   Add a typed reverse-RPC surface such as `host.events.publish`. A successful
   response means the core durably accepted the event under the documented
   delivery class; it does not mean all subscribers processed it.

   Publication must enforce:

   - authenticated plugin/account identity;
   - declared type/version and permission;
   - frame and payload limits;
   - per-plugin/account rate, byte, retained-event, and in-flight quotas;
   - deduplication scope and retention;
   - deadline and cancellation;
   - maximum fan-out known before commit;
   - explicit overload and storage-failure errors.

   Define result DTOs with event ID, accepted/deduplicated state, matched
   subscriber count, durable class, and warnings. Do not synchronously wait for
   every subscriber in the publish call.

6. Integrate event emission with dispatch responses where useful.

   Permit a handler to return a bounded list of emitted events alongside its
   existing actions only if this fits the current protocol cleanly. The host
   validates and accepts them after the handler response. Document exact
   ordering between actions and emitted events and never imply transactionality
   across Telegram/HTTP actions and publication.

   If reverse `host.events.publish` and response-carried events coexist, they
   must share one validator, permission path, quota model, persistence path,
   idempotency semantics, and SDK type. Do not implement two subtly different
   buses.

7. Implement durable fan-out and delivery state.

   For every accepted durable event, create bounded per-subscription delivery
   state. Define a clear state machine such as:

   ```text
   pending -> admitted -> running -> acknowledged
      |          |           |
      +----------+-----------+-> retry_wait -> pending
                                  |
                                  +-> dead_lettered
   ```

   Persist only the minimum necessary event and delivery records. Bound total
   retained bytes, event count, deliveries per event, attempts, history,
   timestamps, and error summaries. Use stable revisions or compare-and-swap
   semantics to prevent concurrent acknowledgement/retry races.

   Reuse the existing per-plugin executor for admission and fairness. Queue
   full must become an explicit pending/retry or rejected state according to
   policy; it must not spawn detached work or drop durable events silently.

8. Define delivery and acknowledgement semantics precisely.

   Durable delivery is at-least-once until acknowledged or dead-lettered. A
   plugin crash after performing an effect but before acknowledgement can cause
   redelivery. State this prominently and provide event ID/deduplication helpers
   so handlers can be idempotent.

   Define:

   - what constitutes acknowledgement;
   - explicit retryable failure versus terminal rejection;
   - timeout, cancellation, process exit, protocol disconnect, malformed
     response, queue overload, and daemon crash behavior;
   - whether acknowledgement is an explicit RPC or successful handler return;
   - attempt number and previous bounded error summary;
   - maximum attempts and deterministic backoff with jitter controlled by a
     fakeable host clock/random source;
   - no retry after a handler reports an ambiguous external mutation unless
     the plugin explicitly resolves it through its own durable idempotency key.

   Ephemeral delivery may be supported as a separate declared class, but it
   must remain bounded and explicitly at-most-once. Never silently downgrade a
   durable declaration to ephemeral behavior.

9. Implement dead-letter and bounded replay operations.

   Provide owner/operator inspection through the existing local control/CLI
   plane and a narrowly permissioned plugin API only if justified. Operations
   may include list, inspect, retry one, discard one, and clear a bounded
   selection. Require explicit confirmation for destructive bulk operations.

   Replay must create a new delivery attempt or a new event with an explicit
   link to the original; choose and document one model. It must preserve source,
   schema version, trace lineage, account/plugin isolation, and current
   subscription compatibility. It must not bypass a removed permission or
   deliver to a newly installed subscriber unless the operator explicitly asks
   for historical replay under a bounded policy.

10. Prevent cycles, storms, and amplification.

   Fairness must prevent one noisy publisher, account, event type, or slow

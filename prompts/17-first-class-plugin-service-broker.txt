TERMINOLOGY

Call the product-level subsystem the Serenox Service Broker. Use conventional
protocol and package names such as `services`, `servicebroker`, `ServiceSpec`,
`ServiceMethodSpec`, `ServiceInvocation`, and `host.services.call`. Do not call
it a “service mesh”: Serenox is mediating local supervised RPC, not installing
network proxies or claiming distributed service-mesh behavior. A future UI may
call the subsystem “Serenox Nexus”, but the wire contract must remain technical
and vendor-neutral.

PRIMARY DELIVERABLE

Implement production-quality, bounded, unary plugin-to-plugin RPC mediated
entirely by the Serenox core. A verified plugin can declare typed services it
provides and exact services it consumes. A caller invokes a logical
service/method/version through a host reverse-RPC API; the core resolves an
active compatible provider, checks signed permissions and dependency policy,
propagates deadline/trace/cancellation, admits the invocation through bounded
execution, and returns a typed result or structured error.

```text
plugin A
  -> host.services.call(ai.summarize/v1, Summarize)
  -> core authentication, policy, resolution and admission
  -> supervised plugin B service handler
  -> typed result
  -> core validation and accounting
  -> plugin A
```

Neither plugin receives the other's PID, executable path, socket, RPC token,
storage namespace, configuration, process handle, or language-specific object.
The core owns discovery, provider identity, compatibility, deadlines,
backpressure, cancellation, circuit state, observability, and lifecycle. The
provider owns the method's business logic.

PRODUCT INTENT

The Service Broker makes plugins reusable workers instead of isolated command
handlers. Example logical contracts include:

```text
speech.transcribe/v1.Transcribe
ai.summarize/v1.Summarize
knowledge.search/v1.Search
notifications.send/v1.Send
```

A Telegram plugin can call an AI service without importing its SDK or receiving
its API key. An AI provider can later be swapped from a remote implementation
to a local model without changing the caller's logical contract. Service names
describe capabilities, not vendors: prefer `ai.summarize` over `openai.chat` in
shared contracts. Vendor-specific services are still allowed when the behavior
is genuinely vendor-specific.

The initial broker is single-daemon and local-process only. It is not gRPC,
HTTP, D-Bus, Kubernetes service discovery, a distributed service mesh, or a
public network API.

NON-GOALS AND HARD BOUNDARIES

Do not add any of the following:

- direct plugin-to-plugin sockets, inherited file descriptors, shared memory,
  direct stdio access, process handles, ports, DNS/service discovery, or tokens;
- raw arbitrary method-name dispatch without signed declarations;
- reflection-driven DTO invocation, arbitrary Go/Python object serialization,
  pickle, gob across trust boundaries, protobuf `Any`, or unrestricted maps;
- streaming RPC in v1; use existing media/blob handles for large content;
- automatic retries of mutating or outcome-unknown provider calls;
- exactly-once invocation or distributed transaction claims;
- caller-selected provider IDs unless an explicit policy grants that choice;
- cross-account service calls by default;
- recursive/unbounded call graphs, circular hard dependencies, fan-out RPC,
  broadcast calls, or hidden fallback chains;
- access to another plugin's storage, jobs, configuration, secrets, logs,
  metrics, events, or action permissions;
- a generic proxy for Telegram, HTTP, SQL, filesystem, shell, or host services;
- invocation payloads, results, IDs, trace IDs, user IDs, or message content in
  metric labels.

2. Define versioned service identity and method contracts.

   Use a stable logical identity such as:

   ```text
   service: ai.summarize
   major version: 1
   method: Summarize
   ```

   Define strict naming, namespace ownership, reserved `serenox.*`/`core.*`
   domains, length/cardinality bounds, and compatibility rules. Major versions
   are routing boundaries. Minor additive schema evolution may be represented
   only if validators and negotiation can enforce it deterministically.

   Define finite DTOs for:

   - service and method specifications;
   - provider declaration and consumer requirement;
   - invocation request/context;
   - result and structured error;
   - provider resolution/health summary;
   - optional schema descriptor/digest;
   - trace, correlation, causation, hop, deadline, attempt, and idempotency
     metadata shared with the Event Fabric where appropriate.

   Host-trusted caller/provider/account identities must never be accepted from
   plugin payload fields.

3. Add signed provider and consumer declarations.

   Extend plugin metadata and `.srnx` policy with declarations similar to:

   ```yaml
   provides:
     - service: ai.summarize
       version: 1
       methods:
         - name: Summarize
           inputSchema: ai.summarize.request/v1
           outputSchema: ai.summarize.result/v1
           effect: read_only
           maxRuntime: 20s

   requires:
     - service: ai.summarize
       version: 1
       methods: [Summarize]
       availability: optional
   ```

   Exact syntax should fit the existing JSON package manifest and handshake DTO
   conventions. Validate package-to-handshake consistency at verify, install,
   activation, restore, upgrade, and rollback. A plugin must not advertise a
   service/method/version or dependency absent from its signed package.

   Bound services per plugin, methods per service, requirements, schema bytes,
   method name lengths, payload/result sizes, max runtime, and total declaration
   size. Reject duplicate providers according to the v1 provider-selection
   policy before publishing readiness.

4. Define method effect and idempotency semantics.

   Every method declares one finite effect class:

   - `read_only`: no externally visible mutation by contract;
   - `idempotent`: mutation is safe only with the supplied idempotency key;
   - `mutating`: may create an external effect and is never auto-retried;
   - `unknown`: conservative default, never auto-retried.

   A declaration is a policy contract, not proof that a third-party API obeys
   it. The broker must not automatically retry any provider call in v1 unless a
   separately reviewed read-only/idempotent policy is implemented with tests.
   Timeout or disconnect after provider admission may be `outcome_unknown`,
   especially for mutating methods.

   Define caller idempotency-key scope, provider visibility, retention, replay,
   duplicate-in-flight behavior, completed-result caching limits, and conflict
   errors. Reuse existing idempotency primitives where semantics match; do not
   create incompatible operation identity rules.

5. Define least-privilege capabilities and permissions.

   Add explicit capabilities such as `services.provide` and `services.consume`.
   Require exact signed permission for each consumed logical service/method,
   for example:

   ```text
   service.call.ai.summarize.v1.Summarize
   ```

   Normalize names deterministically and prevent wildcard widening. Provider
   capability never grants consumer capability. Calling a service never grants
   the caller any of the provider's Telegram, moderation, storage, HTTP, media,
   jobs, control-bot, event, or secret permissions.

   Define separate operator-only permissions for service registry inspection,
   provider override, drain, or administrative health actions. Exhaustively
   test operation-to-permission mapping and package preflight.

6. Implement a bounded provider registry.

   The registry must track only activated, ready, compatible providers and
   their validated method declarations, account scope, active package version,
   health/circuit state, and bounded capacity metadata.

   Choose one deterministic v1 provider policy. Prefer exactly one active
   provider for each `(account, service, major version)` unless the repository
   already has a safe reason to support multiple providers. If multiple
   providers are implemented, define stable priority, operator selection,
   health exclusion, no mid-call failover, upgrade behavior, and anti-flapping
   rules. Do not add load balancing casually.

   Registry changes must be atomic with plugin activation/rollback. Failed
   activation cannot leave ghost providers. A circuit-open, stopped, upgrading,
   or incompatible provider must resolve to a stable unavailable error before
   invocation admission.

7. Validate dependency graphs during activation.

   Distinguish required and optional service requirements. A plugin with a
   missing required dependency must not publish ready. An optional dependency
   produces an explicit unavailable status and may be checked through a typed
   SDK method.

   Build a bounded dependency graph for hard requirements and reject direct or
   indirect cycles before activation. Include the exact cycle path in a bounded
   redacted diagnostic. Optional dependencies must not become hidden hard
   cycles through startup probes.

   Define activation ordering, upgrade, rollback, provider replacement, caller
   drain, and what happens when an already-ready required provider later stops.
   Do not restart dependency trees indefinitely.

8. Implement `host.services.call`.

   Add a typed reverse-RPC operation with request fields for logical service,
   major version, method, bounded JSON payload, optional idempotency key, and
   caller-selected timeout no greater than declared/host limits. The host must
   supply authenticated caller/account identity, invocation ID, absolute
   deadline, trace/correlation/causation context, hop count, and provider
   identity.

   The call path must perform, in order:

   ```text
   validate caller request
     -> check declaration and exact permission
     -> resolve compatible ready provider
     -> check deadline/hop/circuit/capacity
     -> admit through bounded execution
     -> dispatch typed invocation to provider
     -> validate bounded response
     -> return typed result or structured error
   ```

   Define whether admission uses the provider's existing queue or a separate
   bounded service lane within the same executor. Commands, callbacks, jobs,
   Event Fabric deliveries, and service calls must have explicit fairness and
   must not starve each other.

9. Add provider-side service invocation dispatch.

   Extend the supervised protocol with a dedicated invocation kind, not a fake
   Telegram update or stringly command. The provider receives immutable context
   and a validated payload and routes it only to the declared method handler.

   A handler returns a bounded typed payload plus optional metadata/warnings or
   a structured service error. It must not return raw exceptions, stack traces,
   arbitrary action batches, another plugin's objects, or credentials.

   If provider handlers may emit Event Fabric events or perform host actions,
   those operations remain governed by the provider's own signed permissions.
   Document sequencing and non-atomicity. A caller must not be able to lend its
   stronger permissions to the provider, and the provider must not lend its
   permissions to the caller.

10. Make nested calls safe and bounded.

   Support at least `A -> B` reliably. Support `A -> B -> C` only after proving
   the existing duplex connections, pending maps, executor lanes, and sidecar
   event loop cannot deadlock. Enforce:

   - maximum call depth/hop count;
   - one shrinking absolute deadline propagated through the chain;
   - bounded pending calls per plugin/account and globally;
   - call-graph cycle detection using trusted invocation ancestry;
   - deterministic rejection of self-call and `A -> B -> A` unless an explicit
     safe reentrant contract is later added;
   - no blocking while holding registry, executor, storage, or lifecycle locks;
   - cancellation propagation from caller through every admitted descendant;
   - fairness against recursive call amplification.

   If safe nested calls cannot be implemented with the current process
   protocol, ship only depth one and return a stable `nested_call_unsupported`
   error. Do not hide a deadlock risk behind documentation.

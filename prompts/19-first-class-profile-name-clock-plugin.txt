PRODUCT INTENT
Serenox should support small, useful userbot plugins that can update a
bounded part of the account profile through an explicit, least-privilege
interface. This task adds a clock plugin which preserves the user's original
display name, appends a separator and the current local time, and refreshes
the displayed time once per minute:

```text
Original name: Alice
Displayed name: Alice | 14:37
Next minute:   Alice | 14:38
```

The plugin must restore the original profile name when it is disabled,
unloaded, restarted, or otherwise loses ownership of the profile update
lease. It must not continuously create detached goroutines or silently
overwrite a name changed by the user or another authorized component.

OBJECTIVE
Add a first-class typed profile-name mutation and implement an example
`profile.clock` plugin for Go and/or Python using the existing plugin runtime.
The feature must be bounded, restart-safe, permission-controlled, explicit
about time zones and formatting, and honest about Telegram's sequential
mutation and ambiguous-outcome behavior.

REQUIRED WORK
1. Establish the current boundary before changing it.

   Trace and document the existing path from a plugin request through SDK,
   reverse RPC, permission checks, App action application, Telegram
   transport, live gotd adapter, recorded transport, and shutdown. Confirm
   that profile mutations are currently unsupported rather than inferring
   support from DTOs or the generic `ClientOperation` shape. Identify the
   existing typed profile-read fields, if any.

2. Define the profile ownership model.

   Add a core-owned, account-scoped profile update lease or equivalent
   ownership record. At most one active plugin may control the display-name
   fields for an account unless the core explicitly serializes compatible
   writers. The owner must be identified by plugin ID, account ID, and a
   generation/lease token. A stale plugin, old generation, duplicate request,
   or plugin without the declared permission must fail closed.

   Decide and document what happens when:

   - the user changes the name outside Serenox;
   - the daemon restarts;
   - the plugin is unloaded or crashes;
   - the account session disconnects;
   - another profile writer requests the lease;
   - Telegram accepts a mutation but the response is lost.

   Never restore a stale name over a newer user change without an explicit
   ownership check. Do not claim that Telegram profile updates are
   transactional or exactly-once.

3. Add an explicit typed profile action.

   Prefer an additive protocol v1 operation if it can remain compatible. Add
   a narrowly defined action such as `profile_update_name` or an equivalent
   typed `ProfileUpdate` DTO with exact fields for:

   - first name and optional last name, or a clearly documented single
     display-name mapping;
   - profile ownership generation/lease identity;
   - idempotency key;
   - response channel/account scope;
   - whether the request is an acquire, update, or restore operation.

   Do not use `ClientOperation.Value` as a hidden JSON escape hatch. Do not
   expose arbitrary `account.*` or `invoke` method names. Validate UTF-8,
   Telegram name limits, empty-name behavior, separator length, and total
   serialized size. Return a typed result containing the confirmed bounded
   profile fields when Telegram proves them, otherwise return
   `outcome_unknown` with a stable error.

4. Implement the live Telegram mapping.

   Map the typed action to Telegram's MTProto `account.updateProfile`, using
   the installed gotd version and the existing authenticated user session.
   Keep the gotd request and response entirely inside `internal/telegram`.
   Add stable error mapping for invalid first name, about/name limits,
   flood-wait/rate-limit, authorization failure, disconnect, timeout,
   permission failure, and ambiguous acceptance. Do not retry a profile
   mutation automatically after an ambiguous response.

   Confirm whether the adapter can safely preserve first name and last name
   independently. If Telegram's display-name semantics require a different
   mapping, document it and keep the plugin API transport-neutral.

5. Add capability and package permission enforcement.

   Introduce a least-privilege capability/permission such as
   `profile.write` or `telegram.profile.write`. It must be enforced during
   manifest validation, installation/activation, metadata registration,
   reverse RPC admission, action validation, and immediately before the live
   adapter call. Existing message-send or read-client permissions must not
   imply profile-write permission.

   Ensure the permission cannot be smuggled through a generic client action,
   malformed JSON, a forged lease token, or a package metadata omission.

6. Implement scheduling without unbounded plugin timers.

   Prefer the existing typed jobs API for a durable one-minute interval if it
   can invoke the plugin with bounded overlap and cancellation. Otherwise add
   the smallest host-supported lifecycle mechanism needed for a recurring
   plugin callback. Do not create one detached goroutine or timer per update.

   Define:

   - interval semantics and whether the first update happens immediately;
   - timezone source and default;
   - daylight-saving behavior and clock rollback behavior;
   - maximum execution time and overlap policy;
   - missed-tick behavior after downtime;
   - cleanup of the schedule on disable, unload, uninstall, account shutdown,
     and daemon shutdown.

   The displayed format must be configurable only within a bounded contract,
   defaulting to 24-hour `HH:MM`. Use the configured account timezone or an
   explicit plugin setting; never silently depend on the host machine timezone.

7. Implement the example `profile.clock` plugin.

   Provide a minimal, packageable example in the runtime that is already the

ACCEPTANCE CRITERIA
1. A permitted plugin can update the account's profile name through an
   explicit typed action that maps to `account.updateProfile`.
2. `profile.clock` displays `original name | HH:MM`, refreshes no more than
   once per minute, and uses an explicit timezone.
3. The original structured name is preserved and restored on disable and
   normal lifecycle cleanup; stale plugins cannot overwrite newer ownership.
4. No generic Telegram method dispatch, raw Telegram object, session value,
   or arbitrary plugin socket crosses the boundary.
5. Permission, lease, idempotency, limits, cancellation, flood wait, and
   outcome-unknown semantics are validated and tested.
6. Recorded/fake-live tests prove the implementation without credentials;
   any live smoke test is separately gated and restores the original name.
7. Plugin unload, restart, account shutdown, and daemon shutdown release
   schedules and ownership state without unbounded timers or goroutines.
8. Documentation accurately distinguishes verified, partial, live-gated, and
   unsupported behavior.

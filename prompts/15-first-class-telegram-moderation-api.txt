PRIMARY DELIVERABLE

Create a production-quality, transport-neutral moderation API that lets a
verified Serenox plugin safely inspect moderation state and perform explicit
administrative operations through the logged-in Telegram user session.

The finished API must support serious moderation plugins, including owner-only
commands and outgoing no-prefix watchers such as:

```text
reply to a message with "mute 1h"
  -> resolve the replied message and its sender
  -> inspect the chat and participant state
  -> restrict that participant until the requested deadline
  -> edit the owner's outgoing command into a bounded result notice
```

The example syntax is a plugin concern. The core deliverable is a broad typed
moderation surface with exact permissions, bounded requests, typed results,
real gotd mappings, stable errors, lifecycle cleanup, and honest verification.
Do not special-case Russian command words, a particular plugin ID, or one
moderation workflow inside the core.

MODULARITY REQUIREMENT

The API is broad, but the implementation must remain aggressively modular.

- Do not add or leave behind an implementation source file larger than 450
  non-blank lines. Split existing oversized files before adding new surface.
- Keep functions below 80 non-blank lines where practical.
- Split protocol models, validation, permission mapping, service routing,
  gotd participant conversion, member mutations, administrator mutations,
  message moderation, join requests, invite links, forum topics, settings,
  error mapping, SDK facades, and tests by responsibility.
- Use narrow operation-group interfaces. Do not grow `Action`,
  `ClientOperation`, `gotd_actions.go`, `gotd_reads.go`, `actions.py`, or one
  new `moderation.go` into a generic dispatcher.
- Keep every vertical slice buildable and tested. A smaller verified catalog is
  preferable to a large collection of methods that only serialize a request.
- Do not add one goroutine, timer, worker, retry loop, cache, or lock forever
  per chat, user, request, or plugin. Every coordinator and cache must be
  bounded and lifecycle-owned.

PRODUCT INTENT

Serenox is a userbot with a supervised plugin boundary. A moderation plugin
should be able to implement commands, no-prefix outgoing watchers, automatic
rules, admin dashboards, audit summaries, and scheduled unmute/unban flows
without importing gotd, Pyrogram, Telethon, or raw Telegram constructors.

The core owns Telegram credentials, access hashes, request validation,
permissions, rate/resource limits, error conversion, and transport calls. A
plugin receives bounded DTOs and invokes explicit operations. This task must
make moderation broad through typed domains, not through an arbitrary Telegram
method escape hatch.

NON-GOALS AND HARD BOUNDARIES

Do not add any of the following:

- raw gotd/TL objects, constructor IDs, access hashes, session data, API ID,
  API hash, phone numbers, login codes, 2FA passwords, or Bot API tokens across
  the plugin boundary;
- arbitrary `invoke`, `raw_call`, method-name dispatch, JSON-to-TL conversion,
  reflection-based Telegram calls, or a generic `ClientOperation.Value` blob;
- direct plugin access to the Telegram socket/client, filesystem session,
  network connection, Bot API, or control-bot token;
- ownership transfer, account deletion, 2FA/password changes, session
  management, payment operations, phone-number visibility, or other account-
  takeover surfaces;
- silent group migration, automatic channel/discussion rewiring, or hidden
  multi-request scans;
- automatic retries of ambiguous Telegram mutations;
- exactly-once, transactional batch, or atomic mute-plus-notification claims;
- unbounded audit-log/history scans, participant enumeration, invite creation,
  scheduled timers, deduplication state, or diagnostic labels;
- policy that treats any incoming user message as an owner command. Ordinary
  command routing remains owner-only, and a no-prefix moderation trigger must
  be an explicitly outgoing watcher implemented by a plugin.

Use the installed gotd version actually pinned by the repository. If Telegram
or gotd cannot implement an operation with a stable bounded mapping, return an
explicit structured `unsupported` result and document the limitation. Do not
fabricate compatibility.

ACCEPTANCE CRITERIA

1. Go and Python plugins can inspect moderation state and perform the verified
   member, administrator, message, settings, join-request, invite, and forum
   operations through typed SDK groups without importing a Telegram library.
2. A plugin can safely resolve the sender of a replied message, mute/restrict
   that participant, and independently edit the owner's outgoing trigger with
   honest sequential results.
3. Both `.mute 1h` and an exact outgoing reply-only no-prefix `mute 1h`/`мут
   1ч` example are supported at plugin level; incoming users cannot invoke the
   owner-only moderation flow.
4. Every claimed operation has an explicit DTO, validation, capability,
   granular permission, resource limit, core service path, real gotd mapping,
   recorded/fake fixture, SDK parity, tests, and documented verification state.
5. No raw Telegram object, access hash, session credential, invite secret,
   arbitrary method dispatcher, generic JSON parameter blob, or plugin-owned
   Telegram connection crosses the boundary.
6. Rights and restriction booleans are unambiguous, preserve field presence,
   convert correctly to/from gotd, and document inheritance and deadline
   semantics.
7. Basic groups, megagroups, broadcast channels, linked discussions, forums,
   anonymous admins, channel senders, creators, administrators, bots, deleted
   users, and migrations produce explicit supported or unsupported outcomes.
8. Least-privilege permissions prevent reply/send/delete-only plugins from
   muting members and prevent mute-only plugins from promoting admins,
   managing invites, deleting topics, or performing destructive bulk actions.
9. Mutations return typed success/no-op/failure/partial/outcome-unknown results,
   do not fabricate resulting state, do not retry ambiguous outcomes, and do
   not claim mute-plus-notification atomicity.
10. Moderation requests, pages, batches, backend calls, caches, cursors,
    idempotency entries, keyed ordering, strings, results, metrics, and
    lifecycle resources all have tested hard bounds and fair scheduling.
11. Plugin/account/chat/target isolation, idempotency, concurrent operation
    ordering, cancellation, shutdown, restart, upgrade, and rollback are
    deterministic and race-tested without reverting already-applied Telegram
    state blindly.
12. Invite URLs, message content, usernames, IDs, access hashes, reasons, and
    raw Telegram errors do not leak into logs, metrics, diagnostics, fixtures,
    or unrelated plugin results.
13. Existing commands, watchers, text/media actions, action results, reads,
    storage, Jobs, HTTP, control bot, package installation, supervision, and
    lifecycle behavior remain compatible.
14. Compatibility documentation distinguishes source-audited, fake,
    recorded-only, live-gated, partial, and unsupported operations and makes no
    claim of full Telegram/Hikka/Pyrogram/Telethon compatibility.
15. All normal tests are deterministic, credential-free, network-free, and
    non-destructive; any live moderation suite is explicitly gated, uses only
    disposable consenting targets, restores changes, and redacts all identity
    and secret data.
